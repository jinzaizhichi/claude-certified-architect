# Сертифікація Claude Certified Architect — Foundations

## Навчальний посібник (на основі офіційного посібника до іспиту)

---

## Вступ

Сертифікація **Claude Certified Architect — Foundations** підтверджує, що фахівець здатний ухвалювати обґрунтовані компромісні рішення під час упровадження реальних рішень на базі Claude. Іспит перевіряє базові знання Claude Code, Claude Agent SDK, Claude API та Model Context Protocol (MCP) — ключових технологій для створення виробничих застосунків із Claude.

Запитання іспиту ґрунтуються на реалістичних галузевих сценаріях: побудові агентних систем підтримки клієнтів, проєктуванні багатоагентних дослідницьких конвеєрів, інтеграції Claude Code у CI/CD, створенні інструментів продуктивності розробників і вилученні структурованих даних із неструктурованих документів.

---

## Цільовий кандидат

Ідеальний кандидат — **архітектор рішень**, який проєктує та випускає виробничі застосунки з Claude. Варто мати щонайменше 6 місяців практичного досвіду з такими технологіями й підходами:

- **Claude Agent SDK** — багатоагентна оркестрація, делегування субагентам, інтеграція інструментів, хуки життєвого циклу
- **Claude Code** — CLAUDE.md, MCP-сервери, Agent Skills, режим планування
- **Model Context Protocol (MCP)** — інструменти й ресурси для інтеграції з бекендом
- **Проєктування промптів** — JSON-схеми, few-shot приклади, шаблони вилучення даних
- **Контекстні вікна** — робота з довгими документами, передавання контексту між агентами
- **Конвеєри CI/CD** — автоматизований перегляд коду, генерування тестів
- **Ескалація та надійність** — обробка помилок, залучення людини до процесу

## Сценарії іспиту

### Сценарій 1: агент підтримки клієнтів
Ви створюєте агента для обробки повернень, суперечок щодо оплати та проблем з обліковими записами за допомогою Claude Agent SDK. Агент використовує MCP-інструменти (`get_customer`, `lookup_order`, `process_refund`, `escalate_to_human`). Мета — понад 80% вирішених звернень під час першого контакту з доречною ескалацією.

### Сценарій 2: генерування коду за допомогою Claude Code
Ви використовуєте Claude Code для прискорення розробки: генерування коду, рефакторингу, налагодження й документування. Потрібно інтегрувати власні slash-команди та конфігурацію CLAUDE.md, а також розуміти, коли застосовувати режим планування.

### Сценарій 3: багатоагентна дослідницька система
Агент-координатор делегує завдання спеціалізованим субагентам: вебдослідження, аналіз документів, синтез і створення звіту. Система має формувати повні звіти з посиланнями на джерела.

### Сценарій 4: інструменти продуктивності розробників
Агент допомагає інженерам досліджувати незнайомі кодові бази, генерувати шаблонний код та автоматизувати рутинні завдання. Використовуються вбудовані інструменти (Read, Write, Bash, Grep, Glob) і MCP-сервери.

### Сценарій 5: Claude Code для безперервної інтеграції
Інтегруйте Claude Code у конвеєр CI/CD для автоматизованого перегляду коду, генерування тестів і зворотного зв’язку в pull request. Промпти потрібно проєктувати так, щоб мінімізувати хибнопозитивні спрацювання.

### Сценарій 6: вилучення структурованих даних
Система вилучає інформацію з неструктурованих документів, перевіряє вивід за допомогою JSON-схем і підтримує високу точність. Вона має правильно обробляти крайові випадки.

### Сценарій 7: архітектурні шаблони розмовного ШІ
Ви проєктуєте багатокрокові діалогові системи, охоплюючи керування контекстним вікном, збереження інструкцій між ходами, стратегії пам’яті, проєктування інструментів для безпечного виконання та обробку неоднозначних або суперечливих введень користувача.

### Сценарій 8: інструменти агентного ШІ *(вміст відсутній — допоможіть доповнити!)*

# Розділ 1: Claude API — основи взаємодії з моделлю

> Документація: [Messages API](https://platform.claude.com/docs/en/api/messages) | [Проєктування промптів](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview)

## 1.1 Структура API-запиту

Claude API працює за моделлю «запит — відповідь». Кожен запит до Claude Messages API містить:

```json
{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "system": "Ви корисний асистент.",
  "messages": [
    {"role": "user", "content": "Привіт!"},
    {"role": "assistant", "content": "Вітаю!"},
    {"role": "user", "content": "Як справи?"}
  ],
  "tools": [...],
  "tool_choice": {"type": "auto"}
}
```

**Ключові поля:**
- `model` — вибір моделі (`claude-opus-4-6`, `claude-sonnet-4-6`, `claude-haiku-4-5`)
- `max_tokens` — максимальна кількість токенів у відповіді
- `system` — системний промпт (визначає поведінку моделі)
- `messages` — історія розмови (**для збереження зв’язності потрібно надсилати повну історію**)
- `tools` — визначення доступних інструментів
- `tool_choice` — стратегія вибору інструментів

## 1.2 Ролі повідомлень

Масив `messages` використовує три ролі:
- `user` — повідомлення користувача
- `assistant` — відповіді моделі (додаються під час надсилання історії)
- `tool` — результати викликів інструментів (роль явно не задається; вони подаються як блок вмісту `tool_result`)

**Критично важливо:** у кожному API-запиті потрібно надсилати **повну історію розмови**. Модель не зберігає стан між запитами — кожен виклик незалежний.

## 1.3 Поле `stop_reason` у відповіді

Відповідь Claude API містить `stop_reason`, яке вказує, чому модель припинила генерування:

| Значення | Опис | Дія |
|---|---|---|
| `"end_turn"` | Модель завершила відповідь | Покажіть результат користувачу |
| `"tool_use"` | Модель хоче викликати інструмент | Виконайте інструмент і поверніть результат |
| `"max_tokens"` | Досягнуто ліміту токенів | Відповідь обрізано; можливо, потрібно збільшити ліміт |
| `"stop_sequence"` | Зустрінуто стоп-послідовність | Обробіть відповідно до логіки застосунку |

Для агентних систем найважливіші `"tool_use"` та `"end_turn"` — вони керують агентним циклом.

## 1.4 Системний промпт

Системний промпт — спеціальна інструкція, що визначає контекст і правила поведінки. Він:
- не входить до масиву `messages`, а передається окремо в полі `system`;
- має пріоритет над повідомленнями користувача;
- завантажується один раз і діє протягом усієї розмови;
- використовується для визначення ролі, обмежень і формату виводу.

**Важливо для іспиту:** формулювання системного промпту може створювати небажані асоціації з інструментами. Наприклад, інструкція «завжди перевіряй клієнта» може спонукати модель надмірно використовувати `get_customer`, навіть коли це не потрібно.

## 1.5 Контекстне вікно

Контекстне вікно — загальний обсяг тексту (у токенах), який модель може опрацювати за один раз. Воно містить:
- системний промпт;
- повну історію повідомлень;
- визначення інструментів;
- результати інструментів.

**Ключові проблеми контекстного вікна:**

1. **Ефект «загубленого посередині»:** моделі надійно опрацьовують інформацію на початку та в кінці довгого введення, але можуть пропускати деталі посередині. Пом’якшення: розміщуйте ключову інформацію ближче до початку або кінця.

2. **Накопичення результатів інструментів:** кожен виклик додає вивід до контексту. Якщо інструмент повертає понад 40 полів, але важливі лише 5, більшість контексту витрачається марно.

3. **Поступове підсумовування:** під час стискання історії числові значення, відсотки й дати часто губляться та стають нечіткими («приблизно», «орієнтовно», «кілька»).

# Розділ 2: інструменти та `tool_use`

> Документація: [Tool Use](https://platform.claude.com/docs/en/build-with-claude/tool-use)

## 2.1 Що таке `tool_use`

`tool_use` — механізм, який дає Claude змогу викликати зовнішні функції. Модель не виконує код безпосередньо — вона генерує структурований запит на виклик інструмента; ваш код виконує його та повертає результат.

## 2.2 Визначення інструмента

Кожен інструмент визначається за допомогою JSON-схеми:

```json
{
  "name": "get_customer",
  "description": "Знаходить клієнта за електронною адресою або ID. Повертає профіль клієнта, зокрема ім’я, електронну адресу, історію замовлень і стан облікового запису. Використовуйте цей інструмент ПЕРЕД lookup_order для перевірки особи клієнта. Приймає електронну адресу (формат: user@domain.com) або числовий customer_id.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email": {"type": "string", "description": "Електронна адреса клієнта"},
      "customer_id": {"type": "integer", "description": "Числовий ID клієнта"}
    },
    "required": []
  }
}
```

**Критично важливі аспекти опису інструмента:**

1. **Опис — основний механізм вибору.** LLM вибирає інструменти за їхніми описами. Мінімальні описи («Отримує інформацію про клієнта») спричиняють помилки, коли можливості інструментів перетинаються.

2. **Включайте в опис:**
   - що робить і що повертає інструмент;
   - формати введення та приклади значень;
   - крайові випадки й обмеження;
   - коли застосовувати цей інструмент замість подібних альтернатив.

3. **Уникайте** однакових або взаємно перекривних описів. Якщо `analyze_content` і `analyze_document` мають майже однакові описи, модель їх плутатиме.

4. **Вбудовані інструменти проти MCP-інструментів:** агенти можуть віддавати перевагу вбудованим інструментам (Read, Grep) перед MCP-інструментами зі схожою функціональністю. Щоб запобігти цьому, посилюйте описи MCP-інструментів — підкреслюйте конкретні переваги, унікальні дані чи контекст, недоступні вбудованим інструментам.

## 2.3 Параметр `tool_choice`

`tool_choice` керує тим, як модель вибирає інструменти:

| Значення | Поведінка | Коли застосовувати |
|---|---|---|
| `{"type": "auto"}` | Модель вирішує, викликати інструмент чи відповісти текстом | Типовий варіант у більшості випадків |
| `{"type": "any"}` | Модель **мусить** викликати якийсь інструмент | Коли потрібен гарантований структурований вивід |
| `{"type": "tool", "name": "extract_metadata"}` | Модель **мусить** викликати конкретний інструмент | Коли потрібно примусово задати перший крок або порядок виконання |

**Важливі сценарії:**
- `tool_choice: "any"` + кілька інструментів вилучення → модель вибирає найдоречніший, але ви все одно отримуєте структурований вивід;
- примусовий вибір → коли потрібно гарантувати конкретну першу дію (наприклад, `extract_metadata` перед збагаченням даних).

## 2.4 JSON-схеми для структурованого виводу

Використання `tool_use` із JSON-схемами — **найнадійніший** спосіб отримати структурований вивід від Claude. Воно:
- гарантує синтаксично коректний JSON (без пропущених дужок і зайвих ком);
- забезпечує потрібну структуру (обов’язкові поля наявні);
- **не** гарантує семантичну правильність (значення все одно можуть бути помилковими).

**Проєктування схеми — ключові принципи:**

```json
{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["bug", "feature", "docs", "unclear", "other"]
    },
    "category_detail": {
      "type": ["string", "null"],
      "description": "Подробиці, якщо category = 'other' або 'unclear'"
    },
    "severity": {
      "type": "string",
      "enum": ["critical", "high", "medium", "low"]
    },
    "confidence": {
      "type": "number",
      "minimum": 0,
      "maximum": 1
    },
    "optional_field": {
      "type": ["string", "null"],
      "description": "Null, якщо інформацію не знайдено в джерелі"
    }
  },
  "required": ["category", "severity"]
}
```

**Правила проєктування схеми:**
1. **Обов’язкові й необов’язкові поля:** позначайте поле обов’язковим лише тоді, коли інформація завжди доступна. Обов’язкові поля підштовхують модель вигадувати значення, якщо даних немає.
2. **Поля, що допускають `null`:** використовуйте `"type": ["string", "null"]` для інформації, яка може бути відсутня. Модель зможе повернути `null`, а не галюцинувати.
3. **Переліки з `"other"`:** додавайте `"other"` і рядок із деталями, щоб не втрачати дані поза наперед визначеними категоріями.
4. **Значення `"unclear"`:** для випадків, коли модель не може впевнено вибрати категорію — чесне `"unclear"` краще за хибну категорію.

## 2.5 Синтаксичні та семантичні помилки

| Тип помилки | Приклад | Пом’якшення |
|---|---|---|
| **Синтаксична** | Некоректний JSON, неправильний тип поля | `tool_use` із JSON-схемою (усуває) |
| **Семантична** | Суми не збігаються, значення не в тому полі, галюцинація | Перевірки валідації, повторна спроба зі зворотним зв’язком, самовиправлення |

# Розділ 3: Claude Agent SDK — побудова агентних систем

> Документація: [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) | [Хуки](https://platform.claude.com/docs/en/agent-sdk/hooks) | [Субагенти](https://platform.claude.com/docs/en/agent-sdk/subagents) | [Сесії](https://platform.claude.com/docs/en/agent-sdk/sessions)

## 3.1 Що таке агентний цикл

Агентний цикл — базовий шаблон автономного виконання завдань. Модель не просто відповідає, а виконує послідовність дій:

```
1. Надіслати Claude запит з інструментами
2. Отримати відповідь
3. Перевірити stop_reason:
   - "tool_use" -> виконати інструмент, додати результат до історії, повернутися до кроку 1
   - "end_turn" -> завдання завершено, показати результат користувачу
4. Повторювати до завершення
```

**Це підхід, керований моделлю:** Claude вирішує, який інструмент викликати далі, на основі контексту та попередніх результатів інструментів. Це відрізняється від жорстко закодованих дерев рішень із фіксованою послідовністю дій.

**Антишаблони (уникайте):**
- аналіз тексту асистента для виявлення завершення («Завдання виконано»);
- використання довільного ліміту ітерацій (наприклад, `max_iterations=5`) як основної умови зупинки;
- перевірка наявності текстового вмісту у відповіді асистента як сигналу завершення.

**Правильний підхід:** єдиний надійний сигнал завершення — `stop_reason == "end_turn"`.

## 3.2 Налаштування `AgentDefinition`

`AgentDefinition` — об’єкт конфігурації агента в Claude Agent SDK:

```python
agent = AgentDefinition(
    name="customer_support",
    description="Обробляє звернення клієнтів щодо повернень і проблем із замовленнями",
    system_prompt="Ви агент підтримки клієнтів...",
    allowed_tools=["get_customer", "lookup_order", "process_refund", "escalate_to_human"],
    # Для координатора:
    # allowed_tools=["Task", "get_customer", ...]
)
```

**Ключові параметри:**
- `name` / `description` — ідентифікація й опис агента;
- `system_prompt` — системний промпт з інструкціями;
- `allowed_tools` — список дозволених інструментів (принцип найменших привілеїв).

## 3.3 Hub-and-spoke: координатор і субагенти

Багатоагентну архітектуру зазвичай будують як топологію «центр і промені» (hub-and-spoke):

```
          Координатор
        /      |       \
   Субагент1  Субагент2  Субагент3
    (пошук)    (аналіз)   (синтез)
```

**Координатор відповідає за:**
- декомпозицію завдання на підзавдання;
- визначення потрібних субагентів (динамічний вибір);
- делегування роботи субагентам;
- агрегування й перевірку результатів;
- обробку помилок і повторні спроби;
- передавання результатів користувачу.

**Критичний принцип: субагенти мають ізольований контекст.**
- Субагенти **не** успадковують історію розмови координатора автоматично.
- Увесь потрібний контекст потрібно **явно передати** в промпті субагента.
- Субагенти не мають спільної пам’яті між викликами.
- Усе спілкування відбувається через координатора — для спостережуваності та контролю помилок.

## 3.4 Інструмент `Task` для запуску субагентів

Субагенти запускаються через інструмент `Task`:

```python
# allowedTools координатора має містити "Task"
coordinator_agent = AgentDefinition(
    allowed_tools=["Task", "get_customer"]
)
```

**Явне передавання контексту є обов’язковим:**

```
# Погано: субагент не має контексту
Task: "Проаналізуй документ"

# Добре: повний контекст у промпті
Task: "Проаналізуй наведений нижче документ.
Документ: [повний текст документа]
Попередні результати пошуку: [результати вебпошуку]
Вимоги до формату виводу: [схема]"
```

**Паралельний запуск:** координатор може викликати кілька `Task` в одній відповіді — субагенти працюватимуть паралельно:

```
# Одна відповідь координатора містить:
Task 1: "Знайди статті про X"
Task 2: "Проаналізуй документ Y"
Task 3: "Знайди статті про Z"
# Усі три завдання виконуються одночасно
```

## 3.5 Хуки в Agent SDK

Хуки дають змогу перехоплювати й перетворювати дані в певних точках життєвого циклу агента.

**PostToolUse** перехоплює результат інструмента до того, як його буде передано моделі:

```python
# Приклад: нормалізація форматів дат із різних MCP-інструментів
@hook("PostToolUse")
def normalize_dates(tool_result):
    # Перетворити Unix timestamp -> ISO 8601
    # Перетворити "Mar 5, 2025" -> "2025-03-05"
    return normalized_result
```

**Хук перехоплення вихідного виклику** блокує дії, що порушують політику:

```python
# Приклад: блокування повернень понад $500
@hook("PreToolUse")
def enforce_refund_limit(tool_call):
    if tool_call.name == "process_refund" and tool_call.args.amount > 500:
        return redirect_to_escalation(tool_call)
```

**Ключова різниця: хуки й інструкції в промпті**

| Атрибут | Хуки | Інструкції в промпті |
|---|---|---|
| Гарантія | **Детермінована** (100%) | **Імовірнісна** (>90%, але не 100%) |
| Коли застосовувати | Критичні бізнес-правила, фінансові операції, відповідність вимогам | Загальні вподобання, рекомендації, форматування |
| Приклад | Блокувати повернення понад $500 | «Спробуй вирішити проблему до ескалації» |

**Правило:** коли помилка може мати фінансові, юридичні наслідки або наслідки для безпеки, використовуйте хуки, а не промпти.

# Розділ 4: Model Context Protocol (MCP)

> Документація: [MCP](https://modelcontextprotocol.io/) | [Інструменти](https://modelcontextprotocol.io/docs/concepts/tools) | [Ресурси](https://modelcontextprotocol.io/docs/concepts/resources) | [Сервери](https://modelcontextprotocol.io/docs/learn/server-concepts)

## 4.1 Що таке MCP

Model Context Protocol (MCP) — відкритий протокол для підключення зовнішніх систем до Claude. MCP визначає три основні типи ресурсів:

1. **Інструменти** — функції, які агент може викликати для виконання дій (CRUD-операції, API-виклики, виконання команд).
2. **Ресурси** — дані, які агент може прочитати для отримання контексту (документація, схеми баз даних, каталоги вмісту).
3. **Промпти** — наперед визначені шаблони промптів для типових завдань.

## 4.2 MCP-сервери

MCP-сервер — процес, який реалізує протокол MCP і надає інструменти та ресурси. Після підключення до MCP-сервера:
- усі інструменти виявляються автоматично;
- інструменти з усіх підключених серверів доступні одночасно;
- описи інструментів визначають, як модель їх використовуватиме.

## 4.3 Налаштування MCP-серверів

**Конфігурація проєкту (`.mcp.json`)** — для командного використання:

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "jira": {
      "command": "npx",
      "args": ["-y", "mcp-server-jira"],
      "env": {
        "JIRA_TOKEN": "${JIRA_TOKEN}"
      }
    }
  }
}
```

**Ключові моменти:**
- `.mcp.json` зберігається в корені проєкту й керується системою контролю версій;
- змінні середовища (`${GITHUB_TOKEN}`) використовуються для секретів — самі токени не додаються до репозиторію;
- конфігурація доступна всім учасникам проєкту.

**Конфігурація користувача (`~/.claude.json`)** — для особистих або експериментальних серверів:
- зберігається в домашньому каталозі користувача;
- не поширюється через систему контролю версій;
- підходить для особистих експериментів і тестування.

**Вибір серверів:**
- для стандартних інтеграцій (Jira, GitHub, Slack) віддавайте перевагу наявним MCP-серверам спільноти;
- створюйте власні сервери лише для унікальних робочих процесів конкретної команди.

## 4.4 Прапорець `isError` у MCP

Коли MCP-інструмент стикається з помилкою, у відповіді використовується `isError: true`. Це сигналізує агенту, що виклик завершився невдало.

**Структурована помилка (добре):**

```json
{
  "isError": true,
  "content": {
    "errorCategory": "transient",
    "isRetryable": true,
    "message": "Сервіс тимчасово недоступний. Перевищено час очікування під час виклику API замовлень.",
    "attempted_query": "order_id=12345",
    "partial_results": null
  }
}
```

**Загальна помилка (антишаблон):**

```json
{
  "isError": true,
  "content": "Операція завершилася невдало"
}
```

Загальна помилка не дає агенту інформації для ухвалення рішення: повторити спробу, змінити запит чи ескалувати проблему?

## 4.5 Ресурси MCP

Ресурси — це дані, які агент може запитати для отримання контексту без виконання дій:

- каталоги вмісту (наприклад, список усіх завдань проєкту, ієрархічна навігація);
- схеми баз даних (розуміння структури даних);
- документація (довідники API, внутрішні посібники);
- зведення проблем або завдань.

**Перевага ресурсів:** агенту не потрібні розвідувальні виклики інструментів, щоб зрозуміти, які дані існують. Ресурс одразу надає «карту».

# Розділ 5: Claude Code — налаштування та робочі процеси

> Документація: [Claude Code](https://code.claude.com/docs/en/overview) | [Пам’ять / CLAUDE.md](https://code.claude.com/docs/en/memory) | [Skills](https://code.claude.com/docs/en/skills) | [MCP](https://code.claude.com/docs/en/mcp) | [Хуки](https://code.claude.com/docs/en/hooks) | [Субагенти](https://code.claude.com/docs/en/sub-agents) | [GitHub Actions](https://code.claude.com/docs/en/github-actions) | [Headless](https://code.claude.com/docs/en/headless)

## 5.1 Ієрархія CLAUDE.md

CLAUDE.md — файл або набір файлів з інструкціями для Claude Code. Існує трирівнева ієрархія:

```
1. Рівень користувача: ~/.claude/CLAUDE.md
   - Застосовується лише до цього користувача
   - НЕ поширюється через VCS
   - Особисті вподобання та стиль роботи

2. Рівень проєкту: .claude/CLAUDE.md або кореневий CLAUDE.md
   - Застосовується до всіх учасників проєкту
   - Керується через VCS
   - Стандарти кодування й тестування, архітектурні рішення

3. Рівень каталогу: CLAUDE.md у підкаталогах
   - Застосовується під час роботи з файлами в цьому каталозі
   - Правила, специфічні для відповідної частини кодової бази
```

**Поширена помилка:** новий учасник команди не отримує проєктних інструкцій, бо їх розмістили в `~/.claude/CLAUDE.md` (рівень користувача), а не в `.claude/CLAUDE.md` (рівень проєкту).

## 5.2 Синтаксис `@path` (імпортування файлів)

CLAUDE.md може посилатися на зовнішні файли через `@path`, що робить конфігурацію модульною:

```markdown
# CLAUDE.md проєкту

Стандарти кодування описано в @./standards/coding-style.md
Вимоги до тестів наведено в @./standards/testing-requirements.md
Огляд проєкту міститься в @README.md, а залежності — в @package.json
```

**Правила для `@path`:**
- ставте `@` безпосередньо перед шляхом до файлу, без пробілу;
- підтримуються відносні й абсолютні шляхи;
- відносні шляхи визначаються відносно файлу, який містить імпорт;
- максимальна глибина вкладених імпортів — 5.

Це усуває дублювання та дає змогу кожному пакету підключати лише доречні стандарти.

## 5.3 Каталог `.claude/rules/`

`.claude/rules/` — альтернатива монолітному CLAUDE.md, яка дає змогу організувати правила за темами:

```
.claude/rules/
  testing.md          -- правила тестування
  api-conventions.md  -- правила API
  deployment.md       -- правила розгортання
  react-patterns.md   -- шаблони React
```

**Ключова можливість: YAML frontmatter із `paths` для умовного завантаження:**

```yaml
---
paths: ["src/api/**/*"]
---

Для API-файлів використовуйте async/await із явною обробкою помилок.
Кожен endpoint має повертати стандартну обгортку відповіді.
```

```yaml
---
paths: ["**/*.test.tsx", "**/*.test.ts"]
---

Тести мають використовувати блоки describe/it.
Замість жорстко заданих значень використовуйте фабрики даних.
Не імітуйте базу даних — використовуйте тестову базу.
```

**Як це працює:**
- правило завантажується **лише** тоді, коли Claude Code редагує файл, що відповідає шаблону `paths`;
- це заощаджує контекст і токени — нерелевантні правила не завантажуються;
- glob-шаблони дають змогу застосовувати правила за типом файлу незалежно від його розташування, що ідеально для тестів, розкиданих по кодовій базі.

**Коли використовувати `.claude/rules/` із `paths`, а коли CLAUDE.md на рівні каталогу:**
- `.claude/rules/` із `paths` — коли правила стосуються файлів у багатьох каталогах (тести, міграції);
- CLAUDE.md на рівні каталогу — коли правила прив’язані до конкретного каталогу й більше ніде не потрібні.

## 5.4 Власні slash-команди та Skills

> **Примітка:** у поточній версії Claude Code власні команди (`.claude/commands/`) об’єднано зі Skills (`.claude/skills/`). Обидва формати створюють команди `/name`. У посібнику до іспиту згадується `.claude/commands/` — цей формат і далі підтримується.

Slash-команди — багаторазові шаблони промптів, які викликаються через `/name`:

**Формат `.claude/commands/` (застарілий, але підтримується):**

```
.claude/commands/
  review.md        -- /review -- стандартний перегляд коду
  test-gen.md      -- /test-gen -- генерування тестів
```

**Формат `.claude/skills/` (поточний):**

```
.claude/skills/
  review/SKILL.md  -- /review -- із налаштуваннями у frontmatter
  test-gen/SKILL.md
```

**Проєктні команди** (`.claude/commands/` або `.claude/skills/`):
- зберігаються у VCS і доступні всім після клонування репозиторію;
- забезпечують узгоджені робочі процеси в усій команді.

**Користувацькі команди** (`~/.claude/commands/` або `~/.claude/skills/`):
- особисті команди, які не поширюються через VCS;
- призначені для індивідуальних робочих процесів.

## 5.5 Skills — `.claude/skills/`

Skills — розширені команди, налаштовані через frontmatter у SKILL.md:

```yaml
---
context: fork
allowed-tools: ["Read", "Grep", "Glob"]
argument-hint: "Шлях до каталогу для аналізу"
---

Проаналізуй структуру коду у вказаному каталозі.
Сформуй звіт про залежності й архітектурні шаблони.
```

**Параметри frontmatter:**

| Параметр | Опис |
|---|---|
| `context: fork` | Запускає Skill в ізольованому субагенті. Докладний вивід не забруднює основну сесію |
| `allowed-tools` | Обмежує доступні інструменти; це захисний механізм — наприклад, Skill не зможе видаляти файли, якщо відповідний інструмент не дозволено |
| `argument-hint` | Підказка, яка просить вказати аргумент, якщо команду викликано без параметрів |

**Коли використовувати Skill, а коли CLAUDE.md:**
- **Skill** — виклик на вимогу для конкретного завдання: перегляду, аналізу, генерування;
- **CLAUDE.md** — загальні стандарти й правила, що завантажуються завжди.

**Особисті Skills (`~/.claude/skills/`):**
- створюйте особисті варіанти під іншими назвами, щоб не впливати на колег.

## 5.6 Режим планування та пряме виконання

**Режим планування:**
- модель лише досліджує та планує, не вносячи змін;
- використовує Read, Grep і Glob для вивчення кодової бази;
- формує план реалізації, який затверджує користувач;
- забезпечує безпечне дослідження без побічних ефектів.

**Коли використовувати режим планування:**
- великі зміни в десятках файлів;
- кілька правдоподібних підходів, наприклад різні способи визначити межі мікросервісів;
- архітектурні рішення: вибір фреймворку чи структури;
- незнайома кодова база, яку спочатку потрібно зрозуміти;
- міграції бібліотек, що зачіпають понад 45 файлів.

**Коли використовувати пряме виконання:**
- виправлення в одному файлі з чітким стеком викликів;
- додавання однієї перевірки валідації;
- добре зрозумілі й однозначні зміни.

**Комбінований підхід:**
1. Режим планування для дослідження та проєктування.
2. Користувач затверджує план.
3. Пряме виконання для реалізації затвердженого плану.

**Субагент Explore** — спеціалізований субагент для дослідження кодової бази:
- ізолює докладний вивід від основного контексту;
- повертає лише підсумок;
- запобігає вичерпанню контекстного вікна в багатофазних завданнях.

## 5.7 Команда `/compact`

`/compact` — вбудована команда для стискання контексту:
- підсумовує попередню історію, звільняючи контекстне вікно;
- використовується під час довгих дослідницьких сесій, коли контекст заповнюється докладним виводом інструментів;
- ризик: під час підсумовування можуть загубитися точні числові значення, дати й конкретні деталі.

## 5.8 Команда `/memory`

`/memory` — вбудована команда для керування пам’яттю між сесіями:
- відкриває файл `CLAUDE.md` для редагування, даючи змогу зберігати нотатки, вподобання й контекст;
- інформація зберігається між сесіями та автоматично завантажується під час запуску;
- корисна для збереження правил проєкту, вподобань користувача, часто вживаних команд і поточного робочого контексту;
- дає змогу не повторювати ті самі інструкції в кожній сесії.

## 5.9 Claude Code CLI для CI/CD

**Прапорець `-p` (або `--print`):**

```bash
claude -p "Проаналізуй цей pull request на проблеми безпеки"
```

- неінтерактивний режим: опрацьовує промпт, друкує результат у stdout і завершує роботу;
- не очікує введення користувача;
- це єдиний правильний спосіб запуску Claude в конвеєрах CI/CD.

**Структурований вивід для CI:**

```bash
claude -p "Переглянь цей PR" --output-format json --json-schema '{"type":"object",...}'
```

- `--output-format json` — вивід у форматі JSON;
- `--json-schema` — перевірка виводу за схемою;
- результат можна програмно розібрати та автоматично опублікувати як вбудовані коментарі до PR.

**Ізоляція контексту сесії:**
Та сама сесія Claude, яка згенерувала код, часто менш ефективно його перевіряє: модель зберігає контекст власних міркувань і рідше ставить під сумнів свої рішення. Для перегляду використовуйте незалежний екземпляр.

**Запобігання дублюванню коментарів:**
Під час повторного перегляду після нових комітів передавайте попередні результати перегляду в контексті та наказуйте Claude повідомляти лише про нові або невирішені проблеми.

## 5.10 `fork_session` і керування сесіями

**`--resume <session-name>`** відновлює іменовану сесію:

```bash
claude --resume investigation-auth-bug
```

- продовжує попередню розмову зі збереженим контекстом;
- корисно для тривалих досліджень у кількох сесіях;
- ризик: якщо після попередньої сесії файли змінилися, результати інструментів можуть бути застарілими.

**`fork_session`** створює незалежну гілку зі спільного контексту:

```
Дослідження кодової бази
          |
     fork_session
     /           \
Підхід A:       Підхід B:
Redux           Context API
```

- обидві гілки успадковують контекст до точки розгалуження;
- після цього вони розвиваються незалежно;
- корисно для порівняння підходів або стратегій тестування.

**Коли варто почати нову сесію замість відновлення:**
- результати інструментів застаріли через зміни файлів;
- минуло багато часу й контекст деградував;
- краще почати заново з фрази «Ось короткий підсумок того, що ми з’ясували: ...», ніж відновлювати сесію зі старими даними інструментів.

# Розділ 6: проєктування промптів — розширені техніки

> Документація: [Проєктування промптів](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview) | [Anthropic Cookbook](https://github.com/anthropics/claude-cookbooks)

## 6.1 Few-shot промптинг

Few-shot промптинг — додавання до промпту 2–4 прикладів введення й виводу, які демонструють очікувану поведінку.

**Чому few-shot ефективніший за текстові описи:**
- нечітку інструкцію на кшталт «будь точнішим» можна тлумачити по-різному;
- приклад однозначно показує очікуваний формат і логіку рішення;
- модель узагальнює шаблон для нових випадків, а не просто повторює приклади.

**Типи few-shot прикладів і ситуації їх застосування:**

1. **Приклади для неоднозначних сценаріїв:**

```
Запит: "Моє замовлення зламане"
Дія: викликати get_customer -> lookup_order -> перевірити стан.
Обґрунтування: "зламане" може означати пошкоджений товар; потрібні дані замовлення.

Запит: "Покличте менеджера"
Дія: негайно викликати escalate_to_human.
Обґрунтування: клієнт явно просить людину. Не намагайтеся вирішити проблему автономно.
```

2. **Приклади форматування виводу:**

```
Приклад знахідки:
{
  "location": "src/auth/login.ts:42",
  "issue": "SQL-ін’єкція в параметрі username",
  "severity": "critical",
  "suggested_fix": "Використати параметризований запит"
}
```

3. **Приклади для розмежування прийнятного та проблемного коду:**

```javascript
// Прийнятно (не позначати):
const items = data.filter(x => x.active);

// Проблема (позначити):
const items = data.filter(x => x.active == true); // Використовуйте строгу рівність ===
```

4. **Приклади вилучення з різних форматів документів:**

```
Документ із посиланням у тексті:
"Як показано в дослідженні (Smith, 2023), показник становить 42%."
-> {"value": "42%", "source": "Smith, 2023", "type": "inline_citation"}

Документ із посиланням на бібліографію:
"Показник становить 42%. [1]"
-> {"value": "42%", "source": "reference_1", "type": "bibliography"}
```

5. **Приклади неформальних одиниць вимірювання:**

```
Текст: "приблизно дві жмені рису"
-> {"amount": "~100g", "original_text": "дві жмені", "precision": "approximate"}

Текст: "дрібка солі"
-> {"amount": "~1g", "original_text": "дрібка", "precision": "approximate"}
```

Few-shot особливо ефективний для вилучення неформальних і нестандартних одиниць вимірювання, надто різноманітних для суто правилових інструкцій.

**Правила нормалізації формату в промптах:**
У разі використання строгих JSON-схем для структурованого виводу додавайте до промпту правила нормалізації:

```
Нормалізація:
- Дати: завжди ISO 8601 (YYYY-MM-DD); "учора" -> обчислити абсолютну дату
- Валюта: числова сума + код валюти; "п’ять баксів" -> {"amount": 5, "currency": "USD"}
- Відсотки: десятковий дріб; "половина" -> 0.5
```

Це запобігає семантичним помилкам, коли JSON синтаксично коректний, але значення неузгоджені.

## 6.2 Явні критерії замість нечітких інструкцій

**Погано (нечітко):**

```
Перевір коментарі в коді на точність.
Будь консервативним — повідомляй лише про знахідки з високою впевненістю.
```

**Добре (явні критерії):**

```
Позначай коментар як проблемний ЛИШЕ тоді, коли:
1. Коментар описує поведінку, яка СУПЕРЕЧИТЬ фактичній поведінці коду
2. Коментар посилається на неіснуючу функцію або змінну
3. Коментар TODO/FIXME стосується помилки, яку вже виправлено в коді

НЕ позначай:
- Коментарі, які лише стилістично застаріли
- Коментарі з незначними неточностями формулювань
- Відсутні коментарі — це окрема категорія
```

**Визначайте рівні серйозності за допомогою прикладів:**

```
CRITICAL: збій виконання для користувачів
  Приклад: NullPointerException під час обробки платежу

HIGH: вразливість безпеки
  Приклад: SQL-ін’єкція, XSS, відсутність перевірки авторизації

MEDIUM: логічна помилка без негайного впливу
  Приклад: неправильне сортування, помилка на одиницю

LOW: якість коду
  Приклад: дублювання, неоптимальний алгоритм для малого обсягу даних
```

## 6.3 Ланцюжки промптів

Ланцюжок промптів розбиває складне завдання на послідовність сфокусованих кроків:

```
Крок 1: проаналізувати auth.ts (лише локальні проблеми)
       -> Вивід: список проблем в auth.ts

Крок 2: проаналізувати database.ts (лише локальні проблеми)
       -> Вивід: список проблем у database.ts

Крок 3: інтеграційний прохід (міжфайлові залежності)
       -> Вивід: проблеми на межах модулів
```

**Чому це важливо:**
- запобігає **розсіюванню уваги** — коли модель отримує забагато файлів одночасно, вона може пропустити помилки в частині з них і дати поверхові коментарі щодо інших;
- забезпечує стабільну якість аналізу кожного файлу;
- дає змогу окремо аналізувати взаємодії між файлами.

**Коли використовувати ланцюжок промптів, а коли динамічну декомпозицію:**
- **ланцюжок промптів** — передбачувані, повторювані завдання: перегляд коду, міграція файлів;
- **динамічна декомпозиція** — відкриті дослідження, у яких підзавдання стають зрозумілими лише під час виконання.

## 6.4 Шаблон «інтерв’ю»

Перед реалізацією рішення Claude ставить уточнювальні запитання:

```
Claude: "Перш ніж реалізувати кешування API, уточню кілька моментів:
1. Яку стратегію інвалідації кешу ви віддаєте перевагу — TTL чи на основі подій?
2. Чи прийнятні застарілі дані, якщо кеш недоступний?
3. Кешування має бути окремим для кожного користувача чи глобальним?
4. Який очікуваний обсяг даних для кешування?"
```

**Коли це корисно:**
- незнайома предметна область: фінтех, охорона здоров’я, юридичні системи;
- завдання з неочевидними наслідками: стратегії кешування, режими відмови;
- кілька життєздатних підходів, де найкращий вибір залежить від контексту.

## 6.5 Валідація та повторна спроба зі зворотним зв’язком

Коли вилучені дані не проходять перевірку:

```
Крок 1: вилучити дані з документа
Крок 2: перевірити (Pydantic, JSON Schema, бізнес-правила)
Крок 3: якщо є помилка — повторити з контекстом:
  - вихідний документ;
  - попереднє, неправильне вилучення;
  - конкретна помилка: "Поле 'total' = 150, але sum(line_items) = 145. Перевір значення повторно."
```

**Коли повторна спроба буде ефективною:**
- помилки формату, наприклад дата в неправильному форматі;
- структурні помилки, наприклад поле розміщено не там;
- арифметичні неузгодженості, які модель може перевірити повторно.

**Коли повторна спроба НЕ допоможе:**
- інформація відсутня у вихідному документі;
- потрібен зовнішній контекст, наприклад дані містяться в іншому ненаданому документі.

**Pydantic як інструмент валідації:**
Pydantic — бібліотека Python для перевірки даних за схемами. Для іспиту важливі такі моменти:
- **структурна валідація:** типи, обов’язковість і обмеження enum перевіряються в коді після отримання JSON від Claude;
- **семантична валідація:** власні валідатори забезпечують бізнес-логіку, наприклад сума позицій дорівнює підсумку або `start_date < end_date`;
- **цикли «валідація — повторна спроба»:** якщо перевірка Pydantic не пройдена, сформуйте повідомлення про помилку й повторно зверніться до Claude з цим контекстом;
- **генерування JSON Schema:** моделі Pydantic можуть генерувати JSON Schema для `tool_use`, забезпечуючи єдине джерело істини.

## 6.6 Самовиправлення

Шаблон для виявлення внутрішніх суперечностей:

```json
{
  "stated_total": "$150.00",
  "calculated_total": "$145.00",
  "conflict_detected": true,
  "line_items": [
    {"name": "Товар A", "price": 75.00},
    {"name": "Товар B", "price": 70.00}
  ]
}
```

Модель вилучає і заявлене, і обчислене значення. Якщо вони відрізняються, `conflict_detected` дає змогу обробити розбіжність.

# Розділ 7: Message Batches API

> Документація: [Message Batches](https://platform.claude.com/docs/en/build-with-claude/message-batches)

## 7.1 Огляд

Message Batches API дає змогу надсилати пакети запитів для асинхронного опрацювання:

| Атрибут | Значення |
|---|---|
| Економія | **50%** порівняно із синхронними викликами |
| Вікно опрацювання | До **24 годин** (без гарантованого SLA щодо затримки) |
| Багатокрокові виклики інструментів | **Не підтримуються** (один запит = одна відповідь) |
| Зіставлення | Поле `custom_id` для зв’язування запиту й відповіді |

## 7.2 Коли використовувати Batch API, а коли синхронний API

| Завдання | API | Чому |
|---|---|---|
| Перевірка PR перед злиттям | **Синхронний** | Розробник очікує; 24 години неприйнятні |
| Нічний звіт про технічний борг | **Batch** | Результат потрібен до ранку; економія 50% |
| Щотижневий аудит безпеки | **Batch** | Завдання нетермінове; економія 50% |
| Інтерактивний перегляд коду | **Синхронний** | Потрібна негайна відповідь |
| Опрацювання 10 000 документів | **Batch** | Масове опрацювання; економія істотна |

## 7.3 Використання `custom_id`

```json
{
  "custom_id": "doc-invoice-2024-001",
  "params": {
    "model": "claude-sonnet-4-6",
    "max_tokens": 1024,
    "messages": [{"role": "user", "content": "Вилучи дані з: ..."}]
  }
}
```

`custom_id` дає змогу:
- пов’язати результат із вихідним документом;
- у разі помилки повторно надіслати лише невдалі документи;
- не опрацьовувати успішні документи повторно.

## 7.4 Обробка помилок у пакетах

1. Надішліть пакет зі 100 документів.
2. 95 завершуються успішно, 5 — невдало через перевищення ліміту контексту.
3. Визначте невдалі запити за `custom_id`.
4. Змініть стратегію, наприклад розділіть довгі документи на фрагменти.
5. Повторно надішліть лише 5 невдалих документів.

## 7.5 Планування SLA

Якщо результат потрібен через 30 годин, а Batch API може працювати до 24 годин:
- вікно надсилання: 30 - 24 = **6 годин**;
- пакети потрібно надсилати не пізніше ніж за 24 години до кінцевого терміну;
- для частих надсилань розділіть їх на чотиригодинні вікна.

# Розділ 8: стратегії декомпозиції завдань

## 8.1 Фіксовані конвеєри (ланцюжки промптів)

Кожен крок визначено наперед:

```
Документ -> Вилучення метаданих -> Вилучення даних -> Валідація -> Збагачення -> Фінальний вивід
```

**Коли застосовувати:**
- структура завдання передбачувана, наприклад перегляди завжди виконуються за одним шаблоном;
- усі кроки відомі заздалегідь;
- потрібні стабільність і відтворюваність.

## 8.2 Динамічна адаптивна декомпозиція

Підзавдання формуються на основі проміжних результатів:

```
1. "Додати тести до застарілої кодової бази"
2. -> Спочатку: скласти карту структури (Glob, Grep)
3. -> Знайдено: 3 модулі без тестів, 2 — з частковим покриттям
4. -> Пріоритет: почати з модуля платежів через високий ризик
5. -> Під час роботи: виявлено залежність від зовнішнього API
6. -> Адаптація: додати mock зовнішнього API перед написанням тестів
```

# Розділ 9: ескалація та залучення людини

## 9.1 Коли ескалувати до людини

**Тригери ескалації — чіткі правила:**

| Ситуація | Дія |
|---|---|
| Клієнт прямо каже: «Покличте менеджера» | Негайно ескалувати; не намагатися вирішити самостійно |
| Політика не охоплює запит | Ескалувати, наприклад коли правила нічого не кажуть про зрівнювання ціни з конкурентом |
| Агент не може просунутися | Ескалувати після розумної кількості спроб |
| Фінансова операція перевищує поріг | Ескалувати; бажано забезпечити це хуком, а не промптом |
| Під час пошуку клієнта знайдено кілька збігів | Попросити додаткові ідентифікатори; не вгадувати |

**Що НЕ є надійним тригером:**

| Ненадійний метод | Чому він не працює |
|---|---|
| Аналіз тональності | Настрій клієнта не корелює зі складністю випадку |
| Самооцінка впевненості моделі за шкалою 1–10 | Модель може впевнено помилятися; калібрування слабке |
| Автоматичний класифікатор | Надмірне ускладнення; може потребувати навчальних даних, яких у вас немає |

## 9.2 Шаблони ескалації

**Негайна ескалація:**

```
Клієнт: "Я хочу поговорити з менеджером"
Агент: [негайно викликає escalate_to_human]
НЕ ТАК: "Я можу допомогти з вашою проблемою, дозвольте..."
```

**Ескалація після спроби вирішити проблему:**

```
Клієнт: "Мій холодильник зламався через два дні після покупки"
Агент: [перевіряє замовлення, пропонує гарантійну заміну]
Якщо клієнта це не влаштовує -> ескалувати
```

**Нюансована ескалація: визнати емоцію → запропонувати рішення → ескалувати після повторної вимоги:**

```
Клієнт: "Це обурливо, я дуже незадоволений якістю!"
Агент: [визнає розчарування] "Я розумію ваше розчарування."
       [пропонує рішення] "Я можу запропонувати заміну або повернення коштів."
Клієнт: "Ні, я хочу з кимось поговорити!"
Агент: [клієнт наполягає повторно -> негайна ескалація]
```

Ключовий принцип: спочатку визнайте емоцію, потім запропонуйте конкретне рішення й ескалюйте лише тоді, коли клієнт повторно висловлює бажання поговорити з людиною. Не ескалюйте після першого прояву невдоволення — це не те саме, що прохання покликати менеджера.

**Ескалація через прогалину в політиці:**

```
Клієнт: "У конкурента X цей товар на 30% дешевший — дайте мені знижку"
Політика: охоплює коригування цін лише на власному сайті
Агент: [ескалує — політика не охоплює зрівнювання цін із конкурентами]
```

## 9.3 Протоколи структурованого передавання

Під час ескалації агент має передати людині структурований підсумок:

```json
{
  "customer_id": "CUST-12345",
  "customer_name": "Іван Петренко",
  "issue_summary": "Запит на повернення коштів за пошкоджений товар",
  "order_id": "ORD-67890",
  "root_cause": "Товар надійшов пошкодженим; фотографії додано",
  "actions_taken": [
    "Клієнта перевірено через get_customer",
    "Замовлення підтверджено через lookup_order",
    "Запропоновано стандартну заміну — клієнт наполягає на поверненні коштів"
  ],
  "refund_amount": "$89.99",
  "recommended_action": "Схвалити повне повернення коштів",
  "escalation_reason": "Клієнт попросив поговорити з менеджером"
}
```

Людина-оператор не має доступу до повного протоколу розмови — вона бачить лише цей підсумок. Тому він має бути повним і самодостатнім.

## 9.4 Калібрування впевненості та людський нагляд

Для систем вилучення даних:

1. **Оцінки впевненості на рівні полів:** модель повертає оцінку впевненості для кожного вилученого поля.
2. **Калібрування:** використовуйте розмічені валідаційні набори для налаштування порогів.
3. **Маршрутизація:**
   - висока впевненість + стабільна точність → автоматизоване опрацювання;
   - низька впевненість або неоднозначні джерела → перевірка людиною.

**Стратифікована випадкова вибірка:**
- регулярно перевіряйте вибірку навіть серед вилучень із високою впевненістю;
- загальна точність 97% може приховувати 40% помилок для певного типу документів;
- аналізуйте точність за типом документа й за полем, а не лише загалом.

# Розділ 10: обробка помилок у багатоагентних системах

## 10.1 Категорії помилок

| Категорія | Приклади | Можна повторити | Дія агента |
|---|---|---|---|
| **Тимчасова** | Timeout, 503, збій мережі | Так | Повторити з експоненційною затримкою |
| **Валідаційна** | Некоректний формат введення, відсутнє обов’язкове поле | Ні, спочатку виправити введення | Змінити запит і повторити |
| **Бізнесова** | Порушення політики, перевищення порога | Ні | Пояснити користувачу; запропонувати альтернативу |
| **Доступ** | Доступ заборонено | Ні | Ескалувати |

## 10.2 Антишаблони обробки помилок

| Антишаблон | Проблема | Правильний підхід |
|---|---|---|
| Загальний статус «пошук недоступний» | Координатор не може вирішити, як відновитися | Повернути тип помилки, запит, часткові результати й альтернативи |
| Тихе приховування: порожній результат вважається успіхом | Координатор думає, що збігів немає, хоча стався збій | Розрізняти «немає результатів» і «помилка пошуку» |
| Переривання всього процесу через одну помилку | Усі часткові результати втрачаються | Продовжити з частковими результатами й позначити прогалини |
| Нескінченні повторні спроби всередині субагента | Затримка й марнування ресурсів | Локальне відновлення: 1–2 спроби, потім передавання помилки координатору |

## 10.3 Структурована помилка субагента

```json
{
  "status": "partial_failure",
  "failure_type": "timeout",
  "attempted_query": "Вплив ШІ на музичну індустрію 2024",

    {"title": "Звіт про генерування музики за допомогою ШІ", "url": "...", "relevance": 0.8}
  ],
  "alternative_approaches": [
    "Спробувати вужчий запит: 'інструменти ШІ для музичної композиції'",

```

Це надає координатору інформацію, потрібну для рішення:
- повторити спробу зі зміненим запитом;
- використати часткові результати;
- делегувати іншому субагенту;
- продовжити без цього розділу й позначити прогалину.

**Окремий шар контексту:**
У багатоагентних системах кожен субагент працює з обмеженим бюджетом контексту й отримує лише інформацію, потрібну для його завдання. Це запобігає «витоку контексту», коли один агент заповнює вікно інформацією, нерелевантною для інших.

**Обмежені бюджети контексту для субагентів:**
- надсилайте мінімальний контекст: конкретне завдання й потрібні дані;
- наказуйте субагенту повертати структуровані результати, а не необроблені дампи даних;
- використовуйте `allowedTools`, щоб обмежити набір інструментів субагента: менше інструментів означає менше відволікань і нижчу вартість контексту.

## 13.1 Довідник із вибору інструментів

| Завдання | Інструмент | Приклад |
|---|---|---|
| Знайти файли за назвою або шаблоном | **Glob** | `**/*.test.tsx`, `src/components/**/*.ts` |

1. Read — завантажте повний вміст файлу.
2. Програмно змініть вміст.

## 1.1 Проєктування агентних циклів для автономного виконання завдань

### Ключові знання:
- життєвий цикл агентного циклу: надіслати запит Claude, перевірити `stop_reason` (`"tool_use"` або `"end_turn"`), виконати інструменти й повернути результати для наступної ітерації;
- результати інструментів додаються до історії розмови, щоб модель могла вибрати наступну дію;
- ухвалення рішень моделлю, коли Claude сам вибирає наступний інструмент, на відміну від жорстко закодованих дерев рішень.

### Ключові навички:
- керування потоком: продовжувати цикл, коли `stop_reason = "tool_use"`, і зупинятися на `"end_turn"`;
- додавання результатів інструментів до контексту між ітераціями;
- уникнення антишаблонів: аналізу тексту асистента для визначення завершення та довільних лімітів ітерацій як основного механізму зупинки.

## 1.2 Оркестрація багатоагентних систем: координатор і субагенти

### Ключові знання:
- архітектура hub-and-spoke: координатор контролює все міжагентне спілкування, обробку помилок і маршрутизацію;
- субагенти працюють з ізольованим контекстом і не успадковують історію координатора автоматично;
- обов’язки координатора: декомпозиція завдання, делегування, агрегування результатів і динамічний вибір субагентів;
- ризик надто вузької декомпозиції координатором.

### Ключові навички:
- розподіляти дослідницьке покриття між субагентами, мінімізуючи дублювання;
- реалізовувати цикли поступового вдосконалення, у яких координатор оцінює синтез і повторно маршрутизує завдання;
- спрямовувати все спілкування через координатора для спостережуваності.

## 1.3 Налаштування викликів субагентів, передавання контексту й запуск

### Ключові знання:
- інструмент `Task` запускає субагентів; `allowedTools` координатора має містити `"Task"`;
- контекст субагента потрібно явно включати в промпт — субагенти не успадковують контекст батьківського агента;
- конфігурація `AgentDefinition`: описи, системні промпти, обмеження інструментів;
- керування сесіями через `fork_session` для дослідження альтернатив.

### Ключові навички:
- включати повні виводи попередніх агентів у промпт субагента;
- використовувати структуровані формати для відокремлення даних від метаданих під час передавання контексту;
- запускати паралельних субагентів кількома викликами `Task` в одному ході координатора;
- формулювати промпти координатора через цілі й критерії якості, а не покрокові інструкції.

## 1.4 Реалізація багатокрокових процесів із примусовим виконанням і передаванням

### Ключові знання:
- різниця між **програмним примусовим виконанням** через хуки й передумови та **настановами в промпті** щодо порядку процесу;
- коли потрібні детерміновані гарантії, наприклад перевірка особи перед фінансовою операцією, самих промптів недостатньо;
- структуровані протоколи передавання під час ескалації: ID клієнта, причина, рекомендована дія.

### Ключові навички:
- програмні передумови, які блокують наступні виклики, доки не завершено попередні кроки, наприклад блокування `process_refund`, доки `get_customer` не поверне перевірений ID;
- декомпозиція багатоаспектних запитів клієнтів на окремі пункти;
- створення структурованих підсумків під час ескалації людині.

## 1.5 Хуки Agent SDK для перехоплення викликів і нормалізації даних

### Ключові знання:
- шаблони хуків, наприклад `PostToolUse`, для перехоплення результатів інструмента до їх опрацювання моделлю;
- хуки, що перехоплюють вихідні виклики для забезпечення правил відповідності, наприклад блокують повернення коштів понад поріг;
- хуки дають **детерміновані гарантії**, тоді як інструкції в промпті забезпечують лише **імовірнісну відповідність**.

### Ключові навички:
- хуки `PostToolUse` для нормалізації форматів даних: Unix timestamp, ISO 8601, числові коди стану;
- хуки перехоплення для блокування дій, що порушують політику, з перенаправленням на ескалацію;
- вибирати хуки замість промптів, коли бізнес-правила потребують гарантованого виконання.

## 1.6 Стратегії декомпозиції складних робочих процесів

### Ключові знання:
- **фіксовані конвеєри** або ланцюжки промптів проти **динамічної адаптивної декомпозиції** на основі проміжних результатів;
- ланцюжки промптів: послідовні кроки, наприклад окремий аналіз кожного файлу, а потім інтеграційний прохід;
- адаптивні плани дослідження, які формують підзавдання залежно від виявленого.

### Ключові навички:
- застосовувати ланцюжки промптів для передбачуваних багатоаспектних перевірок, а динамічну декомпозицію — для відкритих досліджень;
- розбивати великі перегляди коду на аналіз окремих файлів і окремий міжфайловий інтеграційний прохід;
- декомпозувати відкриті завдання: спочатку скласти карту структури, потім сформувати пріоритетний план.

## 1.7 Стан сесії, відновлення й розгалуження

### Ключові знання:
- `--resume <session-name>` для продовження іменованих сесій;
- `fork_session` для створення незалежних дослідницьких гілок зі спільного контексту;
- важливість повідомляти агенту про зміни файлів під час відновлення сесії;
- нова сесія зі структурованим підсумком може бути надійнішою за відновлення із застарілими результатами.

### Ключові навички:
- використовувати `--resume` для продовження іменованих дослідницьких сесій;
- застосовувати `fork_session` для паралельного порівняння підходів;
- вибирати між відновленням, коли контекст іще актуальний, та новою сесією, коли результати застаріли.

# Домен 2: проєктування інструментів та інтеграція MCP (18%)

## 2.1 Проєктування інтерфейсів інструментів із чіткими описами

### Ключові знання:
- описи інструментів — **основний механізм**, за яким LLM їх вибирає; мінімальні описи роблять вибір ненадійним;
- важливо вказувати формати введення, приклади запитів, крайові випадки й межі застосовності;
- неоднозначні або взаємно перекривні описи спричиняють неправильну маршрутизацію;
- формулювання системного промпту може створювати небажані асоціації з інструментами.

### Ключові навички:
- писати описи, які чітко відрізняють кожен інструмент від подібних альтернатив;
- перейменовувати інструменти, усуваючи функціональне перекриття, наприклад `analyze_content` → `extract_web_results`;
- розділяти універсальні інструменти на спеціалізовані з чіткими контрактами введення й виводу.

## 2.2 Реалізація структурованих відповідей про помилки MCP-інструментів

### Ключові знання:
- прапорець `isError` у відповідях MCP-інструментів;
- різниця між **тимчасовими помилками** на кшталт timeout, **валідаційними помилками** через неправильне введення, **бізнес-помилками** через порушення політики та **помилками доступу або дозволів**;
- загальні помилки на кшталт «Operation failed» не дають правильно вибрати стратегію відновлення;
- різниця між помилками, які можна й не можна повторювати.

### Ключові навички:
- повертати структуровані метадані: `errorCategory` (`transient`, `validation`, `permission`), `isRetryable` і зрозуміле людині повідомлення;
- використовувати `retryable: false` для порушень бізнес-правил із чітким поясненням користувачу;
- виконувати локальне відновлення в субагентах для тимчасових збоїв і передавати вище лише помилки, які вони не можуть усунути;
- відрізняти збій доступу, що потребує рішення про повторну спробу, від коректного порожнього результату без збігів.

## 2.3 Розподіл інструментів між агентами й налаштування `tool_choice`

### Ключові знання:
- надмірна кількість інструментів на агента, наприклад 18 замість 4–5, **знижує** надійність вибору;
- агенти з інструментами поза їхньою спеціалізацією схильні використовувати їх неправильно;
- обмежений доступ до інструментів: лише потрібні для ролі плюс невеликий набір міжрольових утиліт;
- значення `tool_choice`: `"auto"`, `"any"` і примусовий вибір інструмента (`{"type": "tool", "name": "..."}`).

### Ключові навички:
- обмежувати набір інструментів кожного субагента тими, що відповідають його ролі;
- замінювати загальні інструменти обмеженими альтернативами, наприклад `fetch_url` → `load_document`;
- використовувати `tool_choice: "any"`, щоб гарантувати виклик інструмента замість текстової відповіді;
- примусово вибирати конкретний інструмент для забезпечення порядку виконання.

## 2.4 Інтеграція MCP-серверів у Claude Code й агентні процеси

### Ключові знання:
- область дії MCP-сервера: проєктна конфігурація `.mcp.json` для команд і користувацька `~/.claude.json` для експериментів;
- підстановка змінних середовища в `.mcp.json`, наприклад `${GITHUB_TOKEN}`, для керування секретами;
- інструменти всіх підключених MCP-серверів виявляються під час підключення та доступні одночасно;
- ресурси MCP як «каталоги вмісту» — зведення завдань, схеми баз даних — зменшують потребу в розвідувальних викликах.

### Ключові навички:
- налаштовувати спільні MCP-сервери в проєктному `.mcp.json`, використовуючи токени зі змінних середовища;
- зберігати особисті й експериментальні сервери в `~/.claude.json`;
- для стандартних інтеграцій віддавати перевагу MCP-серверам спільноти перед власними.

## 2.5 Вибір і застосування вбудованих інструментів Read, Write, Edit, Bash, Grep і Glob

### Ключові знання:
- **Grep** шукає у вмісті файлів: назви функцій, повідомлення про помилки, імпорти;
- **Glob** знаходить файли за шаблонами назв або розширень;
- **Read/Write** працюють із цілими файлами, а **Edit** виконує точні зміни за унікальним збігом тексту;
- якщо Edit не спрацьовує через неунікальні збіги, використовуйте Read + Write.

### Ключові навички:
- використовувати Grep для пошуку у вмісті, а Glob — для пошуку файлів за шаблонами;
- формувати розуміння поступово: знайти точки входу через Grep, потім простежити потік через Read;
- відстежувати використання функцій через модулі-обгортки.

# Домен 3: налаштування Claude Code і робочі процеси (20%)

## 3.1 Налаштування CLAUDE.md з урахуванням ієрархії, області дії та модульності

### Ключові знання:
- ієрархія CLAUDE.md: користувацький (`~/.claude/CLAUDE.md`), проєктний (`.claude/CLAUDE.md` або кореневий `CLAUDE.md`) і рівень каталогу (`CLAUDE.md` у підкаталогах);
- налаштування рівня користувача діють лише для однієї людини й не поширюються через VCS;
- синтаксис `@path` для посилання на зовнішні файли, наприклад `@./standards/coding-style.md`, і модульної організації CLAUDE.md;
- каталог `.claude/rules/` для тематичних файлів правил замість монолітного CLAUDE.md.

### Ключові навички:
- діагностувати проблеми ієрархії, наприклад коли новий учасник не отримує інструкцій, бо вони збережені на користувацькому, а не проєктному рівні;
- застосовувати `@path`, наприклад `@./standards/testing.md`, щоб вибірково підключати стандарти в CLAUDE.md кожного пакета;
- розділяти великий CLAUDE.md на кілька файлів у `.claude/rules/`: testing.md, api-conventions.md, deployment.md.

## 3.2 Створення й налаштування власних slash-команд і Skills

### Ключові знання:
- **проєктні команди** в `.claude/commands/`, що поширюються через VCS, на відміну від **користувацьких команд** у `~/.claude/commands/`;
- Skills у `.claude/skills/` із frontmatter у `SKILL.md`: `context: fork`, `allowed-tools`, `argument-hint`;
- `context: fork` запускає Skill в ізольованому контексті субагента, не забруднюючи основну сесію;
- особисті варіанти Skills можна зберігати в `~/.claude/skills/` під іншими назвами.

### Ключові навички:
- зберігати проєктні slash-команди в `.claude/commands/`, щоб їх отримувала вся команда;
- застосовувати `context: fork` для ізоляції Skills із докладним виводом;
- використовувати `allowed-tools` для обмеження доступних Skill інструментів;
- застосовувати `argument-hint`, щоб підказувати розробникам обов’язкові параметри.

## 3.3 Правила для конкретних шляхів і умовне завантаження стандартів

### Ключові знання:
- файли `.claude/rules/` можуть містити YAML frontmatter `paths`, який активує правила за glob-шаблонами;
- правила з обмеженням за шляхом завантажуються **лише** під час редагування відповідних файлів, заощаджуючи контекст і токени;
- правила шляхів на основі glob можуть бути кращими за CLAUDE.md на рівні каталогу, коли правила охоплюють багато каталогів, наприклад тести.

### Ключові навички:
- створювати файли `.claude/rules/` із `paths: ["terraform/**/*"]`, щоб вони завантажувалися лише для відповідних файлів;
- використовувати glob-шаблони на кшталт `**/*.test.tsx`, щоб застосовувати правила за типом файлу незалежно від розташування;
- віддавати перевагу правилам за шляхами перед CLAUDE.md рівня каталогу, коли правила поширюються на всю кодову базу.

## 3.4 Вибір між режимом планування та прямим виконанням

### Ключові знання:
- **режим планування** — для складних завдань із великими змінами, кількома життєздатними підходами й архітектурними рішеннями;
- **пряме виконання** — для простих, добре зрозумілих змін, наприклад додавання однієї перевірки;
- режим планування дає змогу безпечно дослідити кодову базу до внесення змін;
- субагент Explore ізолює докладний вивід дослідження.

### Ключові навички:
- використовувати режим планування для завдань з архітектурними наслідками: мікросервіси, міграції понад 45 файлів;
- застосовувати пряме виконання для виправлень із чітким стеком викликів в одному файлі;
- використовувати субагента Explore, щоб запобігти вичерпанню контекстного вікна в багатофазних завданнях;
- комбінувати підходи: планування для дослідження, виконання для реалізації.

## 3.5 Ітеративне вдосконалення

### Ключові знання:
- конкретні приклади введення й виводу — найефективніший спосіб пояснити очікування;
- **ітерація на основі тестів:** спочатку написати тести, потім удосконалювати рішення за результатами невдалих перевірок;
- шаблон «інтерв’ю»: Claude ставить запитання, щоб виявити неочевидні аспекти проєктування;
- коли надавати всі проблеми одним повідомленням — якщо вони взаємозалежні, а коли послідовно — якщо вони незалежні.

### Ключові навички:
- наводити 2–3 конкретні приклади введення й виводу для уточнення вимог до перетворення;
- до реалізації створювати набори тестів з очікуваною поведінкою, крайовими випадками й вимогами до продуктивності;
- використовувати шаблон «інтерв’ю» для виявлення аспектів проєктування: інвалідації кешу, режимів відмови;
- надавати конкретні тестові випадки з прикладами введення й очікуваного виводу для крайових ситуацій.

## 3.6 Інтеграція Claude Code у конвеєри CI/CD

### Ключові знання:
- прапорець `-p` або `--print` для неінтерактивного режиму в автоматизованих конвеєрах;
- `--output-format json` і `--json-schema` для структурованого виводу в CI;
- CLAUDE.md надає контекст проєкту — стандарти тестування й критерії перегляду — для Claude Code, запущеного з CI;
- **ізоляція контексту сесії:** та сама сесія, яка згенерувала код, перевіряє його гірше за незалежний екземпляр.

### Ключові навички:
- запускати Claude Code у CI з `-p`, щоб процес не зависав в очікуванні інтерактивного введення;
- використовувати `--output-format json` + `--json-schema` для структурованих результатів, наприклад вбудованих коментарів до PR;
- передавати результати попереднього перегляду під час повторного запуску після нових комітів і повідомляти лише про нові або невиправлені проблеми;
- документувати стандарти тестування й доступні fixtures у CLAUDE.md, щоб поліпшити якість генерування тестів;
- додавати наявні тестові файли до контексту під час генерування нових тестів, щоб уникати дублювання й дотримуватися стилю.

# Домен 4: проєктування промптів і структурований вивід (20%)

## 4.1 Проєктування промптів із явними критеріями для підвищення точності

### Ключові знання:
- явні критерії ефективніші за нечіткі інструкції, наприклад «позначай коментарі лише тоді, коли вони суперечать коду» краще за «перевір точність коментарів»;
- загальні настанови на кшталт «будь консервативнішим» працюють гірше за конкретні категорійні критерії;
- вплив хибнопозитивних спрацювань на довіру розробників: висока частота хибних знахідок в окремих категоріях підриває довіру навіть до точних категорій.

### Ключові навички:
- визначати критерії перегляду: про що повідомляти — помилки, безпека — і що ігнорувати — дрібний стиль;
- тимчасово вимикати категорії з високою часткою хибнопозитивних спрацювань;
- задавати явні критерії серйозності з прикладами коду для кожного рівня.

## 4.2 Few-shot промптинг для стабільнішого виводу

### Ключові знання:
- few-shot приклади — найефективніший спосіб отримувати стабільно відформатований і практичний вивід;
- few-shot може показувати обробку неоднозначних випадків: вибір інструмента, прогалини в тестовому покритті;
- few-shot допомагає моделі узагальнювати нові шаблони, а не лише повторювати типові відповіді;
- few-shot може зменшувати галюцинації у завданнях вилучення.

### Ключові навички:
- надавати 2–4 цільові приклади неоднозначних сценаріїв з обґрунтуванням;
- включати приклади очікуваного формату: місце, проблема, серйозність, запропоноване виправлення;
- наводити приклади, що відрізняють прийнятні шаблони коду від реальних проблем;
- показувати правильне вилучення з документів різної структури.

## 4.3 Забезпечення структурованого виводу через `tool_use` і JSON-схеми

### Ключові знання:
- `tool_use` із JSON-схемами — найнадійніший спосіб гарантувати відповідність схемі й усунути синтаксичні помилки JSON;
- з `tool_choice: "auto"` модель може повернути текст; із `"any"` вона мусить викликати інструмент; примусовий вибір задає конкретний інструмент;
- строгі JSON-схеми усувають синтаксичні помилки, але не запобігають семантичним: суми можуть не збігатися, значення можуть потрапляти не в ті поля;
- проєктування схеми: обов’язкові й необов’язкові поля, enum із `"other"` та полем деталей для розширюваності.

### Ключові навички:
- визначати інструменти вилучення з JSON-схемами й розбирати дані з результатів `tool_use`;
- використовувати `tool_choice: "any"`, щоб гарантувати структурований вивід за наявності кількох схем;
- примусово викликати конкретний інструмент: `tool_choice: {"type": "tool", "name": "extract_metadata"}`;
- робити поля необов’язковими або nullable, якщо джерело може не містити інформації, щоб уникати вигаданих значень;
- застосовувати enum-значення `"unclear"` і `"other"` разом із полями деталей для розширюваної категоризації.

## 4.4 Валідація, повторні спроби й цикли зворотного зв’язку для якості вилучення

### Ключові знання:
- повторна спроба зі зворотним зв’язком про помилку: включайте конкретні помилки валідації в наступний промпт, щоб спрямувати виправлення;
- повторні спроби неефективні, якщо інформації просто немає в джерелі;
- проєктування циклу зворотного зв’язку: відстежуйте шаблон, який спричинив знахідку, у полі `detected_pattern`;
- семантичні помилки, наприклад неузгоджені підсумки, на відміну від синтаксичних, які усуває `tool_use`.

### Ключові навички:
- формувати наступні промпти з вихідним документом, неправильним вилученням і конкретними помилками валідації;
- визначати, коли повторна спроба не допоможе, наприклад коли потрібна інформація є лише в зовнішньому документі;
- включати `detected_pattern` у знахідки для аналізу хибнопозитивних спрацювань;
- проєктувати самовиправлення через вилучення і `calculated_total`, і `stated_total` для виявлення розбіжностей.

## 4.5 Проєктування ефективних стратегій пакетного опрацювання

### Ключові знання:
- Message Batches API: економія 50%, вікно опрацювання до 24 годин, без гарантій SLA щодо затримки;
- пакетне опрацювання підходить для неблокувальних завдань — нічних звітів, аудитів — і не підходить для блокувальних, наприклад перевірок перед злиттям;
- Batch API не підтримує багатокрокові виклики інструментів у межах одного запиту;
- поля `custom_id` зіставляють запити й відповіді в пакетах.

### Ключові навички:
- використовувати синхронний API для блокувальних перевірок, а Batch API — для нічних і щотижневих навантажень;
- планувати частоту надсилання пакетів за вимогами SLA, наприклад чотиригодинні вікна для гарантії 30 годин із 24-годинним опрацюванням;
- повторно надсилати лише невдалі документи, визначені за `custom_id`;
- удосконалювати промпти на вибірці перед масштабним запуском.

## 4.6 Багатоекземплярні й багатопрохідні архітектури перегляду

### Ключові знання:
- обмеження самоперевірки: модель зберігає контекст власних міркувань і рідше ставить під сумнів свої рішення;
- незалежні екземпляри перегляду без контексту генерування краще знаходять тонкі проблеми;
- багатопрохідний перегляд: локальний аналіз кожного файлу плюс міжфайловий інтеграційний прохід, щоб уникнути розсіювання уваги.

### Ключові навички:
- використовувати другий незалежний екземпляр Claude для перегляду змін без контексту генерування;
- розділяти перегляд кількох файлів на проходи по кожному файлу та інтеграційні проходи для аналізу міжфайлового потоку даних;
- використовувати перевірочні проходи із самооцінкою впевненості для каліброваної маршрутизації переглядів.

# Домен 5: керування контекстом і надійність (15%)

## 5.1 Керування контекстом розмови для збереження критичної інформації

### Ключові знання:
- ризики поступового підсумовування: числа, відсотки й дати стискаються до нечітких формулювань;
- ефект «загубленого посередині»: моделі надійно опрацьовують початок і кінець довгого введення, але можуть пропустити знахідки посередині;
- виводи інструментів можуть накопичуватися в контексті непропорційно до їхньої корисності, наприклад понад 40 полів замість потрібних 5;
- важливість надсилати повну історію розмови в наступних API-запитах.

### Ключові навички:
- вилучати транзакційні факти в постійний блок «факти справи» поза підсумованою історією;
- скорочувати докладні виводи інструментів до потрібних полів;
- розміщувати ключові знахідки на початку агрегованих даних із явними заголовками розділів;
- вимагати від субагентів включати метадані — дати, джерела — у структурований вивід.

## 5.2 Ефективні шаблони ескалації та усунення неоднозначності

### Ключові знання:
- доречні тригери ескалації: пряме прохання залучити людину, прогалини або винятки в політиці, неможливість просунутися;
- негайна ескалація для прямого прохання на відміну від спроби вирішити проблему в межах компетенції агента;
- аналіз тональності й самостійна оцінка впевненості моделі — ненадійні замінники оцінки складності випадку;
- кілька збігів клієнтів потребують запиту додаткових ідентифікаторів, а не евристичного вгадування.

### Ключові навички:
- визначати явні критерії ескалації з few-shot прикладами в системному промпті;
- негайно виконувати прямі прохання про людину без додаткового розслідування;
- ескалувати, коли політика неоднозначна або не охоплює конкретний запит;
- просити додаткові ідентифікатори, коли результати інструмента містять кілька збігів.

## 5.3 Стратегії передавання помилок у багатоагентних системах

### Ключові знання:
- структурований контекст помилки — тип збою, запит, часткові результати, альтернативи — дає координатору змогу розумніше відновлюватися;
- потрібно відрізняти збої доступу, де timeout вимагає рішення про повтор, від коректних порожніх результатів без збігів;
- загальні статуси на кшталт «пошук недоступний» приховують цінний контекст від координатора;
- і тихе приховування, і переривання всього процесу через один збій є антишаблонами.

### Ключові навички:
- повертати структурований контекст помилки: тип збою, що було виконано, часткові результати, можливі альтернативи;
- відрізняти збої доступу від коректних порожніх результатів;
- виконувати локальне відновлення в субагентах для тимчасових збоїв, а вище передавати лише невідновні помилки разом із частковими результатами;
- позначати покриття в синтезі: що добре підтверджено, а де залишаються прогалини.

## 5.4 Ефективне керування контекстом під час дослідження великих кодових баз

### Ключові знання:
- деградація контексту в довгих сесіях: модель починає давати нестабільні відповіді й посилатися на «типові шаблони» замість конкретних класів;
- файли-чернетки зберігають ключові знахідки між межами контексту;
- делегування субагентам ізолює докладний дослідницький вивід;
- структуроване збереження стану дає змогу відновитися після збою.

### Ключові навички:
- запускати субагентів для конкретних запитань, залишаючи високорівневу координацію головному агенту;
- зберігати ключові знахідки у файлах-чернетках і посилатися на них пізніше;
- підсумовувати ключові знахідки перед запуском субагентів наступної фази;
- використовувати `/compact` для зменшення використання контексту під час довгих досліджень.

## 5.5 Робочі процеси з людським наглядом і калібруванням упевненості

### Ключові знання:
- агреговані метрики, наприклад загальна точність 97%, можуть приховувати слабкі результати для окремих типів документів або полів;
- стратифікована випадкова вибірка вимірює частоту помилок серед вилучень із високою впевненістю;
- калібрування впевненості на рівні полів за розміченими валідаційними наборами;
- перед автоматизацією потрібно перевіряти точність за типом документа й сегментом поля.

### Ключові навички:
- реалізовувати стратифіковану випадкову вибірку для виявлення нових шаблонів помилок;
- аналізувати точність за типом документа й полем, підтверджуючи стабільність;
- повертати оцінки впевненості на рівні полів і калібрувати пороги перевірки за розміченими даними;
- спрямовувати вилучення з низькою впевненістю або неоднозначним джерелом на перевірку людиною.

## 5.6 Збереження походження й обробка невизначеності в синтезі з кількох джерел

### Ключові знання:
- під час підсумовування атрибуція губиться, якщо не зберігати відповідності «твердження → джерело»;
- структуровані відповідності потрібно зберігати під час агрегування;
- суперечливі статистичні дані слід позначати з атрибуцією, а не довільно вибирати одне значення;
- дати публікації або збору даних допомагають не сприймати часові відмінності як суперечності.

### Ключові навички:
- вимагати від субагентів відповідності «твердження → джерело»: URL, назва документа, цитати;
- структурувати звіти так, щоб відділяти стабільні знахідки від спірних;
- зберігати суперечливі значення з примітками й передавати їх координатору для узгодження;
- включати дати публікації для правильного часового тлумачення;
- форматувати за типом вмісту: фінансові дані як таблиці, новини як текст, технічні знахідки як структуровані списки.

# Приклади екзаменаційних запитань із поясненнями

## Запитання 1 (сценарій: агент підтримки клієнтів)

**Ситуація:** дані показують, що у 12% випадків агент пропускає `get_customer` і викликає `lookup_order`, використовуючи лише ім’я клієнта, що призводить до неправильних повернень коштів.

**Яка зміна буде найефективнішою?**

- A) Додати програмну передумову, яка блокує `lookup_order` і `process_refund`, доки не отримано ID через `get_customer` **[ПРАВИЛЬНО]**
- B) Поліпшити системний промпт
- C) Додати few-shot приклади
- D) Реалізувати класифікатор маршрутизації

**Чому A:** коли критична бізнес-логіка вимагає конкретної послідовності інструментів, програмне забезпечення дає **детерміновані гарантії**, яких не можуть забезпечити підходи на основі промптів B і C. Варіант D стосується доступності, а не порядку інструментів.

## Запитання 2 (сценарій: агент підтримки клієнтів)

**Ситуація:** агент часто викликає `get_customer` замість `lookup_order` для запитань щодо замовлень. Описи інструментів мінімальні й подібні.

**Що потрібно зробити насамперед?**

- A) Додати few-shot приклади
- B) Розширити опис кожного інструмента форматами введення, прикладами й межами застосування **[ПРАВИЛЬНО]**
- C) Додати шар маршрутизації
- D) Об’єднати інструменти

**Чому B:** описи інструментів — основний механізм їх вибору моделлю. Це виправлення потребує найменше зусиль і дає найбільший ефект. A додає токени, не усуваючи першопричину. C — надмірне ускладнення. D потребує більше роботи, ніж виправдано.

## Запитання 3 (сценарій: агент підтримки клієнтів)

**Ситуація:** агент вирішує лише 55% проблем за цілі 80%. Він ескалює прості випадки та намагається автономно обробляти складні винятки з політики.

**Як поліпшити калібрування?**

- A) Додати явні критерії ескалації з few-shot прикладами **[ПРАВИЛЬНО]**
- B) Використовувати самооцінку впевненості 1–10 з автоматичною ескалацією
- C) Навчити окремий класифікатор на історичних даних
- D) Використовувати аналіз тональності

**Чому A:** це безпосередньо усуває першопричину — нечіткі межі рішень. B ненадійний, бо модель може впевнено помилятися. C — надмірне ускладнення. D розв’язує іншу проблему: настрій не дорівнює складності.

## Запитання 9 (сценарій: багатоагентна дослідницька система)

**Як зменшити накладні витрати, зберігши надійність?**

- A) Надати агенту синтезу обмежений інструмент `verify_fact` для простих перевірок, а складні й далі спрямовувати через координатора **[ПРАВИЛЬНО]**
- B) Накопичувати всі потреби в перевірці в пакет і повернути їх координатору наприкінці
- C) Надати агенту синтезу повний доступ до всіх інструментів вебпошуку

**Чому A:** це застосування принципу найменших привілеїв. Агент синтезу отримує саме те, що потрібно для 85% типових випадків, а складні дослідження й далі проходять через координатора. B створює блокувальні залежності: пізніші кроки синтезу можуть залежати від раніше перевірених фактів. C порушує розподіл відповідальності. D покладається на спекулятивне кешування, яке не може надійно передбачити потреби.

## Запитання 11 (сценарій: Claude Code для CI)

**Ситуація:** команда хоче знизити вартість API для автоматизованого аналізу. Claude зараз обслуговує два процеси в реальному часі: 1) блокувальну перевірку перед злиттям, яка має завершитися до того, як розробник зможе злити PR; 2) нічний звіт про технічний борг для перегляду вранці. Менеджер пропонує перевести обидва на Message Batches API заради економії 50%.

**Як оцінити цю пропозицію?**

- A) Використати пакетне опрацювання лише для звітів про технічний борг, а перевірки перед злиттям залишити в реальному часі **[ПРАВИЛЬНО]**
- B) Перевести обидва процеси на пакетне опрацювання й опитувати стан завершення
- C) Залишити обидва в реальному часі, щоб уникнути проблем із порядком пакетних результатів
- D) Перевести обидва на пакетне опрацювання з переходом у реальний час, якщо пакет виконується надто довго

**Чому A:** Message Batches API заощаджує 50%, але опрацювання може тривати до 24 годин без гарантованого SLA щодо затримки. Тому він не підходить для блокувальних перевірок перед злиттям, коли розробники очікують, але ідеальний для нічних пакетних завдань на кшталт звітів про технічний борг.

## Запитання 12 (сценарій: перегляд коду з кількох файлів)

**Ситуація:** pull request змінює 14 файлів у модулі обліку запасів. Однопрохідний перегляд усіх файлів дає неузгоджені результати: докладні коментарі для одних файлів, поверхові для інших, пропущені очевидні помилки й суперечливий зворотний зв’язок, коли однаковий шаблон в одному файлі позначено проблемним, а в іншому схвалено.

**Як перебудувати перегляд?**

- A) Розділити на сфокусовані проходи: окремо аналізувати кожен файл на локальні проблеми, потім виконати окремий інтеграційний прохід для міжфайлових потоків даних **[ПРАВИЛЬНО]**
- B) Вимагати від розробників розділяти великі PR на групи по 3–4 файли
- C) Перейти на модель вищого рівня з більшим контекстним вікном і переглядати всі 14 файлів за один прохід
- D) Виконати три незалежні повні перегляди PR і повідомляти лише про проблеми, знайдені щонайменше у двох

**Чому A:** сфокусовані проходи безпосередньо усувають першопричину — розсіювання уваги під час опрацювання багатьох файлів. Аналіз кожного файлу забезпечує стабільну глибину, а окремий інтеграційний прохід знаходить міжфайлові проблеми. B перекладає тягар на розробників, не поліпшуючи систему. C — хибне уявлення: більше контекстне вікно не виправляє якість уваги. D приховує реальні помилки, вимагаючи консенсусу між неузгодженими виявленнями.

**Чому B:** перейменування на `extract_web_results` і явна згадка вебпошуку та URL безпосередньо усувають першопричину — семантичне перекриття назв і описів. Призначення кожного інструмента стає однозначним.

**Чому C:** підсумок ключових знахідок на початку використовує ефект первинності, поміщаючи критичне в найнадійнішу позицію. Явні заголовки допомагають моделі орієнтуватися у вмісті посередині й прямо пом’якшують ефект «загубленого посередині».

## Запитання 16 (Сценарій: Claude Code для безперервної інтеграції)

**Ситуація:** Ваш CI-конвеєр запускає CLI Claude Code (у режимі `--print`) і використовує CLAUDE.md для передавання контексту проєкту під час перевірки коду. Загалом розробники вважають такі перевірки змістовними. Однак вони повідомляють, що інтегрувати знайдені проблеми в робочий процес складно: Claude виводить описові абзаци, які доводиться вручну копіювати в коментарі до PR. Команда хоче автоматично публікувати кожне зауваження як окремий вбудований коментар до PR у відповідному місці коду. Для цього потрібні структуровані дані з шляхом до файлу, номером рядка, рівнем серйозності та запропонованим виправленням. Який підхід буде найефективнішим?

**Який підхід найефективніший?**

Агент зазвичай розв’язує лише одну проблему або змішує параметри різних запитів. Який підхід найефективніше підвищить надійність для повідомлень із кількома проблемами?

**Який підхід найефективніший?**

- A) Реалізувати шар попередньої обробки, який окремим викликом моделі розбиває повідомлення з кількома проблемами на окремі запити, обробляє кожен незалежно й об’єднує результати.

- C) Додати до промпту few-shot-приклади, які демонструють правильне міркування та послідовність викликів інструментів для запитів із кількома проблемами. **[ПРАВИЛЬНО]**

**Чому C:** Few-shot-приклади, які демонструють правильне міркування й послідовність інструментів для запитів із кількома проблемами, найефективніші, тому що агент уже добре працює з одиничними проблемами. ## Запитання 56 (Сценарій: Агент підтримки клієнтів)

**Ситуація:** Журнали робочого середовища показують стабільну закономірність: коли клієнти вживають у повідомленні слово «обліковий запис», наприклад «Я хочу перевірити в обліковому записі замовлення, яке зробив учора», агент у 78% випадків спочатку викликає `get_customer`. Коли схожий запит сформульовано без слів «обліковий запис», наприклад «Я хочу перевірити замовлення, яке зробив учора», він у 93% випадків спочатку викликає `lookup_order`. **Яка першопричина найімовірніша?**

- A) Системний промпт містить інструкції, чутливі до ключових слів, які спрямовують поведінку за термінами на кшталт «обліковий запис» і створюють ненавмисні шаблони вибору інструментів. **[ПРАВИЛЬНО]**

# Практичні вправи

## Вправа 1: Агент із кількома інструментами та логікою ескалації

**Мета:** Спроєктувати цикл агента з інтеграцією інструментів, структурованою обробкою помилок та ескалацією.

**Кроки:**
1. Визначте 3–4 MCP-інструменти з докладними описами; додайте два схожі інструменти для перевірки правильності вибору
2. Реалізуйте цикл агента з перевіркою `stop_reason` (`"tool_use"` / `"end_turn"`)
3. Додайте структуровані відповіді про помилки: `errorCategory`, `isRetryable`, опис
4. Реалізуйте hook-перехоплювач, який блокує операції вище заданого порога й спрямовує їх на ескалацію
5. Протестуйте запити з кількома аспектами

**Домени:** 1 (Архітектура агентів), 2 (Інструменти та MCP), 5 (Контекст і надійність)

---

## Вправа 2: Налаштування Claude Code для командної розробки

**Мета:** Налаштувати CLAUDE.md, власні команди, правила для окремих шляхів та MCP-сервери.

**Кроки:**
1. Створіть CLAUDE.md рівня проєкту з універсальними стандартами
2. Створіть файли `.claude/rules/` із YAML-frontmatter для різних ділянок коду (`paths: ["src/api/**/*"]`, `paths: ["**/*.test.*"]`)
3. Створіть проєктний skill у `.claude/skills/` із `context: fork` та `allowed-tools`
4. Налаштуйте MCP-сервер у `.mcp.json` зі змінними середовища та особисте перевизначення в `~/.claude.json`
5. Перевірте режим планування й пряме виконання на завданнях різної складності

**Домени:** 3 (Налаштування Claude Code), 2 (Інструменти та MCP)

---

## Вправа 3: Конвеєр вилучення структурованих даних

**Мета:** JSON Schema, `tool_use` для структурованого виводу, цикли перевірки й повторних спроб, пакетна обробка.

**Кроки:**
1. Визначте інструмент вилучення з JSON Schema: обов’язкові й необов’язкові поля, enum із варіантом `"other"`, nullable-поля
2. Побудуйте цикл перевірки: у разі помилки повторіть спробу, передавши документ, неправильний результат вилучення та конкретну помилку перевірки
3. Додайте few-shot-приклади для документів із різною структурою
4. Використайте пакетну обробку через Message Batches API: 100 документів, обробка помилок за допомогою `custom_id`
5. Додайте маршрутизацію до людей: оцінки впевненості на рівні полів та аналіз типу документа

**Домени:** 4 (Проєктування промптів), 5 (Контекст і надійність)

---

## Вправа 4: Проєктування й налагодження багатоагентного дослідницького конвеєра

**Мета:** Оркестрація субагентів, передавання контексту, поширення помилок і синтез із відстеженням джерел.

**Кроки:**
1. Створіть координатора з двома або більше субагентами (`allowedTools` містить `"Task"`, контекст явно передається в промптах)
2. Запускайте субагентів паралельно кількома викликами `Task` в одній відповіді
3. Вимагайте структурований вивід субагента: твердження, цитата, URL джерела, дата публікації
4. Зімітуйте тайм-аут субагента: поверніть координатору структурований контекст помилки й продовжте з частковими результатами
5. Протестуйте суперечливі дані: зберігайте обидва значення із зазначенням джерел; відокремлюйте підтверджені результати від спірних

**Домени:** 1 (Архітектура агентів), 2 (Інструменти та MCP), 5 (Контекст і надійність)

| **Claude API** | `tool_use` із JSON Schema, `tool_choice` (`"auto"` / `"any"` / примусовий вибір), `stop_reason`, `max_tokens`, системні промпти |
| **Message Batches API** | Економія 50%, вікно до 24 годин, `custom_id`, відсутність багатоходових викликів інструментів |
| **JSON Schema** | Обов’язкові й необов’язкові поля, nullable-поля, типи enum, `"other"` із деталізацією, strict mode |
| **Pydantic** | Перевірка схеми, семантичні помилки, цикли перевірки й повторних спроб |
| **Вбудовані інструменти** | Read, Write, Edit, Bash, Grep, Glob — призначення та критерії вибору |
| **Few-shot-промптинг** | Цільові приклади для неоднозначних ситуацій, узагальнення на нові шаблони |
| **Ланцюжки промптів** | Послідовна декомпозиція на сфокусовані проходи |
| **Контекстне вікно** | Бюджети токенів, поступове узагальнення, «втрата в середині», scratchpad-файли |
| **Керування сеансами** | Відновлення, `fork_session`, іменовані сеанси, ізоляція контексту |
| **Калібрування впевненості** | Оцінювання на рівні полів, калібрування на розмічених наборах, стратифікована вибірка |

- Розгортання або хостинг MCP-серверів: інфраструктура, мережі, оркестрація контейнерів

- Constitutional AI, RLHF або методики навчання безпеки

- Computer use: автоматизація браузера, взаємодія з робочим столом

- Налаштування для конкретних хмарних провайдерів: AWS, GCP, Azure

# Рекомендації з підготовки

1. **Створіть агента за допомогою Claude Agent SDK** — реалізуйте повний цикл агента з викликами інструментів, обробкою помилок і керуванням сеансом. Попрактикуйтеся із субагентами та явним передаванням контексту.

2. **Налаштуйте Claude Code для реального проєкту** — використайте ієрархію CLAUDE.md, правила для окремих шляхів у `.claude/rules/`, skills із `context: fork` та `allowed-tools`, а також інтеграцію MCP-сервера.

3. **Проєктуйте й тестуйте MCP-інструменти** — пишіть описи, що чітко розрізняють схожі інструменти, повертайте структуровані помилки з категоріями та прапорцями можливості повтору, тестуйте неоднозначні запити користувачів.

4. **Побудуйте конвеєр вилучення даних** — використовуйте `tool_use` із JSON Schema, цикли перевірки й повторних спроб, необов’язкові та nullable-поля, а також пакетну обробку через Message Batches API.

5. **Практикуйте проєктування промптів** — додавайте few-shot-приклади для неоднозначних сценаріїв, явні критерії перевірки й багатопрохідні архітектури для великих перевірок коду.

6. **Вивчіть шаблони керування контекстом** — виділяйте факти з багатослівного виводу, використовуйте scratchpad-файли та делегуйте дослідження субагентам для роботи з обмеженнями контексту.

7. **Зрозумійте ескалацію та участь людини** — коли ескалювати: прогалини в політиці, явний запит користувача, неможливість просунутися; як працюють процеси маршрутизації за рівнем упевненості.

8. **Пройдіть практичний іспит** перед справжнім. Він використовує ті самі сценарії та формат.
